# M7 — Unified Generative Audiovisual Instrument

**Status:** Active programme. Current implementation branch: main. M7-C0 acceptance is complete; M7-C1 is the active milestone.  
**Governing reference:** [IDM Visual Instrument — Visual Composition, Generative Art & Live Concert Architecture](guides/IDM_Visual_Instrument_Visual_Composition_Generative_Art_and_Live_Concert_Architecture.md).

The Volume 11 manual is the project's governing creative and architectural reference for M7. Its distinction between musical fact, audio observation, visual intention and visual outcome estimate is normative. Implementation plans must preserve its requirements for visual identity, lineage, reproducibility, performer agency, perceptual hierarchy, live reliability and safety. Any deliberate deviation must be documented with a rationale.

## Product direction

AVTranslator is evolving from a collection of video, generator and effect layers into a generative visual composition instrument: a system that can create and remember visual objects, develop recurring motifs, compose phrases and scenes, interpret musical structure without merely reacting to signal levels, and remain directly performable by an artist.

M7 must build on the existing renderer, composition, layers, effects, audio analysis, OSC control, modulation, performance sets and operator workspace. It must not replace the existing rendering architecture wholesale.

## Architectural constraints

1. **Preserve the existing Layer as the renderable unit.** A higher-level VisualObject references a layer; it does not replace it.
2. **Keep visual models renderer-independent.** No Qt, ModernGL, GPU handles, textures or frame buffers in the visual ontology.
3. **Preserve project and set compatibility.** New serialized fields are additive where possible; old projects must load with deterministic legacy objects.
4. **Keep preview and projector GPU ownership independent.** Visual identity and authored state may be shared; GL resources may not.
5. **Separate musical fact, audio observation, visual intention and visual estimate.** Do not silently infer musical semantics from RMS or spectral features.
6. **Keep performer agency explicit.** Automatic direction must respect locks, overrides, safety limits and the ability to hold, freeze, recover or choose a scene.
7. **Bound all live work.** Queues, GPU simulation budgets, event processing, rasterization and history must have defined limits.
8. **Measure before optimizing.** Do not claim a GPU bottleneck or a performance improvement from CPU submission timing alone.
9. **Treat safety as runtime behaviour.** A future safety profile must take precedence over normal mappings, automation and operator macros.
10. **Use the Volume 11 manual as the governing reference.** Its vocabulary, feature specification template and acceptance checklists guide new work.

**Authored motif and lineage contract (C0):**

- A visual motif is an authored, persistent concept with its own stable motif_id; it is not a VisualObject, a layer ID, or a musical Motif. The relationship to a musical motif is explicit mapping data, not shared identity.
- A motif may have multiple visual-object realizations. Each VisualObject remains associated with exactly one renderable Layer in C0. Similarity, shared palette, or generator type never creates motif membership automatically.
- VisualObject.lineage.motif_id is an explicit reference. It is inherited only when the author or a declared transformation policy requests it; otherwise it remains unset. The actual authored VisualMotif record, owner/edit policy, invariants, versioning and composition-owned registry are M7-C1 responsibilities.
- An ordinary transform preserves the object's object_id and motif reference. Replacing its source creates a new object identity with the replaced object as its parent and provenance source.
- Duplication creates a new object ID, records the source as parent and source, and inherits the motif reference only by explicit policy.
- Fracture creates a new object ID for each child; each child records the fractured object as parent/source and explicitly inherits its motif reference when the fragments remain instances of that motif.
- Assembly creates a new composite object ID. Its ordered, unique source_object_ids list records every contributing object; parent_object_id remains unset unless one source is genuinely designated as the primary parent. Assembly does not invent a motif membership.
- Motif return creates a new object ID linked to the existing authored motif_id, with origin=motif_return and provenance to the actual historical instances used. It does not resurrect or reuse an old object ID.
- source_object_ids and parent_object_id are historical provenance references, not foreign keys requiring the source instances to remain in the active composition registry. The current VisualObject.layer_id ↔ Layer.visual_object_id association remains strict and one-to-one.

C0 stores and validates these references, but does not yet expose a motif editor or implement fracture/assembly rendering. Those behaviours must be implemented by M7-C1 through explicit, bounded transformations that respect the visual object's mutation contract.

## M7-C0 architectural audit findings

The first audit identified these boundaries:

- Layer is the authoritative renderable composition item. Generators, video decks and overlays all enter the composition as layers.
- Composition.add_layer/remove_layer are the central composition-level lifecycle operations; LayerManager is the application-facing create/update/remove boundary.
- Application owns generator, overlay, performance and project services. It creates/replaces compositions on reset, project load and performance-scene recall.
- ProjectManager persists Composition.to_dict(); performance scene snapshots also store Composition.to_dict(); performance sets store the composition dictionary. An additive composition field therefore reaches all three paths without changing renderer code.
- Locked-scene recall previously replaced entries directly in candidate.layers. That bypassed registry maintenance. It now uses Composition.replace_layer() and carries the live locked object's identity forward.
- LayerManager.update_layer() previously allowed arbitrary updates, including identity fields, and mutated live objects before all validation. It now stages candidate layers, validates known fields/contracts, requires explicit source-replacement intent and commits through Composition.replace_layer(). VisualMutationAdapter uses that same boundary for automated target mutations.
- Preview and projector own independent GL contexts. The visual ontology contains data only and creates no GPU resources.
- A focused pytest suite has been restored and is part of the Windows Quality workflow. The C0 acceptance run verifies 34 tests; wider subsystem and hardware coverage remains a continuing programme.

### C0 mutation and event integration

- LayerManager stages deep-copied candidates, validates known fields and mutation contracts before commit, and replaces the layer/registry only after validation. Generic source-defining updates are rejected unless explicitly marked as source replacement. VisualMutationAdapter accepts detached candidate callbacks or bounded property maps and commits all changed Layer fields as one transaction. The default contract vocabulary includes generator settings, layer FX and overlay playback fields; historical serialized default allow-lists are expanded in memory without widening custom restrictive contracts.
- Locked layers reject LayerManager updates/removal by default. VisualMutationAdapter rechecks the lock at commit time. Operator locking first cancels active AUTO PERF layout morphs and attempts to restore temporary peak boosts and per-layer modifier baselines while the layer is still writable; after the lock commits, all adapters refuse further mutations. Existing manual-override windows remain authoritative.
- Visual timeline entries are serialized inside the pre-existing `performance_timeline` payload; historical events remain valid because the new event type is additive. The current executor handles a deliberately small, safe subset and reports unsupported event types rather than guessing renderer semantics.

### C0 data ownership

- A VisualObject is associated with exactly one Layer in the current C0 model.
- Composition.visual_objects is the authoritative registry; the layer stores the stable foreign key visual_object_id.
- Removing a layer removes its associated visual-object record. A recurring VisualMotif is a separate authored entity and may have multiple VisualObject realizations; it must not overload the one-to-one object/layer association. The C0 motif registry/editor and motion grammar are intentionally deferred to C1.
- A source replacement creates a new object ID and points its lineage parent to the previous object. Transform changes do not create a new identity.
- Old composition payloads without visual_objects are migrated in memory by synthesizing deterministic legacy objects. Representative pre-ontology .eliav/.eliset fixtures verify package composition, embedded scenes, stable IDs, and save/load round-trips without a project or set version bump.
- Visual events can be authored as entries in the existing bar/beat Performance Timeline. They use its stable same-position insertion order, one-shot fired-ID set, rewind semantics and application-tick execution; no additional clock, scheduler or queue is created. Initial execution is intentionally limited to reveal, conceal, fade, move and rotate, with missing/locked targets skipped safely. Other ontology event types remain descriptive until their layer/GPU semantics are designed.

## Cross-milestone acceptance principles

Every M7 milestone must specify its artistic intention, musical relationship, visual entities, generation method, inputs/outputs, identity and mutation rules, time/synchronization, resource budget, live controls, safety, failure behaviour, tests and observable acceptance criteria. Use the feature specification template in the Volume 11 manual.

A milestone is not complete merely because a panel or shader exists. Completion requires:
- documented model and ownership boundaries;
- deterministic state and persistence where relevant;
- bounded runtime work and recoverable failure behaviour;
- performer-visible controls and manual override precedence;
- tests for data contracts and lifecycle seams;
- target hardware validation for GPU/performance changes;
- explicit safety review for flashing, pattern and high-motion changes.
